# 3-1 Redis用途決定メモ

## 結論

Redis の適用先は、**`/home` 表示用の集約API（`/api/home`）のレスポンスキャッシュ** に絞る。

## 対象

- 対象画面：`/home`
- 対象API：`GET /api/home`
- 実装対象ファイル候補：`my-app/app/api/home/route.ts`

## この用途を選ぶ理由

- `/home` は家族情報、コスト概要、備蓄品数、料金プラン、保存済みプランなどを集約表示する画面であり、取得データが多くなりやすい
- ユーザーが繰り返し開く画面なので、キャッシュの効果を体感しやすい
- デプロイ後の確認でも、`/home` の表示速度を改善したいという目的に合っている
- Redis を1用途だけに絞ることで、実装範囲を広げすぎずに導入できる
- MVPの主動線に近く、発表時にも「なぜ Redis を使ったか」を説明しやすい

## 今回見送る用途

### プラン生成結果キャッシュ

- デプロイ後、プラン生成と結果表示はすでにかなり高速だった
- 今回の優先課題は `/home` の表示改善であるため、優先度を下げる

### AI説明補助結果キャッシュ

- 追加価値はあるが、日常的に最も体感しやすいのは `/home` の方
- MVPの主要導線への影響度を優先して今回は見送る

### 商品一覧キャッシュ

- 効果は見込めるが、今回の「表示を速くしたい」という課題に対して `/home` ほど直接的ではない

## キャッシュ方針

- キャッシュキー：`home:{userId}`
- TTL：まずは **30秒〜60秒** で開始する
- ユーザーごとに内容が異なるため、共通キーではなく userId を含める
- 更新系処理後は、必要に応じて該当ユーザーのキャッシュ削除を行う

## 想定する更新系トリガー

`/home` の表示内容に影響する更新があった場合、対象ユーザーのキャッシュ削除を検討する。

例：

- 家族情報の登録・更新・削除
- 保存済みプランの保存・削除
- 備蓄品の登録・削除
- 課金状態の変更
- 解約反映

## 実装方針メモ

- `GET /api/home` でまず Redis を参照する
- キャッシュがあればそれを返す
- キャッシュがなければ通常通りデータを集約して返す
- 返却前に Redis へ保存する
- Redis 障害時はキャッシュを使わず通常処理にフォールバックする

## 採用判断

**Redis は `/home` の表示速度改善のために、`/api/home` のレスポンスキャッシュ用途で導入する。**
