# 非機能設計書

## 1. ドキュメント情報

- ドキュメント名：そなえアレ 非機能設計書
- 対象システム：食物アレルギー家庭向け防災備蓄支援アプリ「そなえアレ」
- 対象範囲：MVP
- 作成日：2026年4月7日
- 作成者：チームB

---

## 2. 目的

本書は、食物アレルギー家庭向け防災備蓄支援アプリ「そなえアレ」のMVPにおける非機能要件および非機能設計方針を定義することを目的とする。

本システムは、食物アレルギーのある家庭が、家族条件に合った「食べられる備え」を迷わず準備し、商品候補の確認、購入、備えプランの保存、備蓄商品の登録、賞味期限管理、通知による確認まで継続できる状態を支援することを目指す。

MVPでは、商用大規模サービス水準の厳密なSLAや高度な運用基盤の整備を目指すのではなく、4人・3週間の開発体制において実装可能であり、かつ安定してデモおよび利用ができる現実的な水準を確保することを重視する。

---

## 3. 前提

### 3.1 システム構成上の前提

本システムでは、以下の技術スタックを採用する。

- Frontend：Next.js + TypeScript + Tailwind CSS
- Backend：Next.js Route Handlers
- DB / Auth：Supabase
- Cache：Upstash Redis
- Payment：Stripe
- AI：OpenAI API
- Container：Docker / Docker Compose
- メール送信：外部メール送信サービス
- 定期実行：バッチ / cron 実行基盤

### 3.2 業務・機能上の前提

MVPで対象とする主要機能は以下のとおりである。

- ユーザー登録 / ログイン / ログアウト
- 家族情報・アレルギー情報の登録 / 編集
- AIによる備えプランの作成（提案）
- 防災食（28品目不使用食品）および日常転用品（28品目不使用食品）の候補表示
- 商品サイトへの外部リンク遷移
- 備えプラン保存 / 一覧 / 詳細 / 削除
- 備蓄品一覧表示
- 備蓄品一覧画面内での備蓄商品登録
- 備蓄商品の削除
- 賞味期限管理
- 初期費用・年間維持コスト・備蓄コスト目安の見える化
- ダッシュボード表示
- 賞味期限30日前のメール通知
- 通知メールから備蓄品一覧画面への導線
- 有料機能の解放（決済連携）
- 無料 / 有料の保存件数制御
- バリデーション
- ログ出力
- Redis を用いた最小限のキャッシュ利用

### 3.3 MVPで対象外とする事項

以下はMVPでは対象外とする。非機能設計においても、これらを前提に過剰な対策は行わない。

- 備えプラン編集
- 備蓄商品編集
- 見直し専用画面
- ECサイト内での購入完結
- 価格・在庫のリアルタイム取得
- 商品情報の自動スクレイピング
- 商品成分表の自動解析
- LINE通知
- ブラウザプッシュ通知
- 通知条件の細かいカスタマイズ
- 高度な通知履歴管理画面
- 医療的な最終安全判定
- 本格的な管理者向け商品運用画面
- 複雑なレコメンド / 比較アルゴリズム
- プランの版管理 / 差分比較 / 共同編集

### 3.4 データ・通知・課金に関する前提

本システムの非機能設計では、以下を前提とする。

- 認証は Supabase Auth を利用し、認証情報とアプリ側業務データを分離する
- 商品情報は固定商品マスタとして products テーブルで管理する
- 備えプランは「生成」と「保存」を分け、保存済み備えプランのみDBに保持する
- 備蓄商品は商品マスタからの選択登録と自由入力登録の両方を許容する
- 通知はメールのみとし、賞味期限30日前に1日1回のバッチ処理で送信する
- 各備蓄商品に対する30日前通知は1回のみとする
- 同日に通知対象となった商品は、ユーザー単位で1通のメールにまとめて送信する
- 有料 / 無料の判定は subscriptions と plans_master を参照して行う
- 有料機能による差分は、保存済み備えプラン件数の制限解除のみとする
- AIは備えプラン作成（提案）および説明補助に利用するが、最終安全判定や医療判断は行わない
- 削除は物理削除を基本とする

### 3.5 非機能設計で重視する事項

本システムのMVPでは、以下を特に重視する。

- 認証されたユーザーのみが自分のデータへアクセスできること
- 通知メール送信処理が定期実行で安定して動作すること
- 備えプラン取得や商品一覧表示で待機時間をできるだけ短くすること
- 主要操作、エラー、決済結果、通知処理結果などを追跡できること
- 商品情報やAI提案を最終的な安全保証として見せないこと
- 高度な冗長構成ではなく、MVPに必要十分な可用性を確保すること

## 4. 非機能上の主要リスク

本システムにおいて、MVP段階で特に注意すべき非機能上の主要リスクは以下のとおりである。

| リスク | 内容 | 想定影響 | 基本対策 |
| --- | --- | --- | --- |
| 認可不備 | 他ユーザーの家族情報、備えプラン、備蓄情報、契約情報が参照・更新できてしまう | 重大な情報漏えい | Supabase RLS とサーバー側の本人チェックを併用する |
| 通知重複・通知漏れ | 通知バッチの不具合により同一商品への重複通知または通知漏れが発生する | ユーザー体験低下、運用混乱 | stock_items.notified_30days_at と notification_logs により重複防止と送信履歴管理を行う |
| Stripe Webhook の二重反映 | 同一イベントが複数回処理される | 契約状態の不整合 | 署名検証とイベント単位の冪等制御を行う |
| AI / 外部API失敗 | OpenAI API の遅延・失敗により提案や説明補助が返らない | 一部機能停止、体験低下 | タイムアウト、代替表示、縮退運用を行う |
| 商品情報の過信 | 商品情報やAI説明が最終保証として受け取られる | 誤判断リスク | 注意文を明示し、AIの役割を説明補助に限定する |
| ログ不足 | 障害時に原因調査ができない | 復旧遅延 | 主要操作・エラー・通知・決済に関するログを記録する |
| ダッシュボード集計の遅延 | 一画面に情報を集約しすぎて表示が重くなる | 体感品質低下 | 取得項目の絞り込みとインデックス活用を行う |                                             |

## 5. 非機能設計方針

### 5.1 基本方針

本システムの非機能設計は、商用大規模サービス水準の厳密なSLA達成を目的とするものではなく、MVPとして安定利用とデモ実施が可能な水準を確保することを目的とする。

そのため、以下の方針を採用する。

- 少人数で実装・運用できることを優先する
- 壊れやすい機能に対して重点的に対策を行う
- 高度な冗長化や監視基盤よりも、再実行可能性と障害切り分けのしやすさを重視する
- 設計対象は、運用設計、性能設計、ログ設計、可用性設計、セキュリティ設計の5観点とする
- 対応ブラウザは PC ブラウザを優先し、Google Chrome、Microsoft Edge、Safari 等の主要ブラウザを想定する
- スマホ表示は崩れないレスポンシブ対応を目指すが、MVPではPC優先とする

## 6. 運用設計

### 6.1 目的

本番環境におけるシステム運用を、少人数の開発体制でも破綻なく継続できる状態にすることを目的とする。

### 6.2 設計方針

- 日常運用で確認すべき対象を限定し、少人数でも回る運用とする
- 定期バッチ、メール送信、課金Webhook、AI API呼び出しを重点運用対象とする
- 商品マスタは固定データとして管理し、MVPでは専用管理画面を設けない
- 外部サービス障害時は、機能停止ではなく縮退運用を優先する

### 6.3 設計内容

#### 6.3.1 環境運用

- ローカル開発環境は Docker / Docker Compose を用いて構築する
- 本番環境は HTTPS が有効な環境で運用する
- 秘密情報は環境変数で管理し、リポジトリに含めない
- 開発環境・本番環境で、Stripe、Supabase、OpenAI、Redis、メール送信設定を分離する

#### 6.3.2 定期バッチ運用

- 通知バッチは1日1回実行する
- バッチ処理の流れは以下とする
  1. 賞味期限30日前の商品を抽出する
  2. 既に通知済みでない商品を判定する
  3. ユーザー単位で通知対象商品を集約する
  4. メール送信を実行する
  5. 送信成功後に stock_items.notified_30days_at を更新する
  6. notification_logs に送信履歴を記録する
- バッチ実行結果として、対象ユーザー数、送信件数、失敗件数を確認可能とする

#### 6.3.3 課金運用

- 決済は Stripe Checkout を利用し、カード情報は自前で保持しない
- Stripe Webhook を受信し、契約状態を subscriptions に反映する
- 契約状態の判定は subscriptions を正本とする
- 課金状態は最小限の契約情報管理を優先し、複雑な決済履歴管理はMVPでは行わない

#### 6.3.4 商品マスタ運用

- 商品マスタは固定データとして products テーブルで管理する
- MVPでは商品運用用の管理画面は設けず、seedデータまたは手動更新で対応する
- 商品情報の自動収集やスクレイピングは行わない
- 商品情報はユーザーに過信させないよう、必要な注意文表示を前提とする

#### 6.3.5 障害時運用

- AI機能が失敗した場合は、備えプラン提案・説明補助のみを縮退停止とし、他機能は継続利用可能とする
- Redis 障害時はキャッシュを利用せずに継続動作する
- 通知バッチ失敗時は、失敗ログを確認し、必要に応じて手動再実行可能とする
- Webhook処理失敗時は、Stripeの再送を前提に再受信可能な構成とする

### 6.4 対応内容

- 通知バッチの定期実行
- メール送信結果の確認
- Webhook失敗確認
- OpenAI API失敗時の縮退運用
- 環境変数管理
- 商品マスタの手動運用ルール

### 6.5 対象外内容

- 24時間監視体制
- 管理者向け運用ダッシュボード
- 商品マスタ専用管理画面
- 複雑なジョブ管理基盤
- 本格的なオンコール体制

### 6.6 実装・運用時の注意点

- 通知バッチは再実行時に二重送信が発生しないように設計する
- notified_30days_at の更新タイミングと notification_logs の記録順序を明確にする
- Webhookの開発環境・本番環境の接続先混同を防ぐ
- 毎日確認する対象は、通知処理、決済連携、主要エラーに絞る

## 7. 性能設計

### 7.1 目的

一般利用時に主要画面が快適に表示され、AI生成や通知処理が極端な遅延を起こさない状態を実現することを目的とする。

### 7.2 設計方針

- 最適化対象は主要画面と重い処理に限定する
- 高トラフィック前提の構成は採用しない
- 安定して応答を返すことを優先し、一部機能に限定してキャッシュを利用する
- 同一条件の提案結果はキャッシュを活用して応答速度を向上させる

### 7.3 設計内容

#### 7.3.1 対象画面・処理

MVPで性能上の重点対象とする画面・処理は以下とする。

- ダッシュボード
- 保存済み備えプラン一覧
- 備えプラン詳細
- 備蓄品一覧
- 備えプラン生成API
- AI説明補助API
- 商品一覧表示
- 通知対象抽出バッチ

#### 7.3.2 画面表示方針

- 一般的な家庭向けWebアプリとして、主要画面は快適に表示されることを目標とする
- 備えプラン取得や商品一覧表示では、待機時間をできるだけ短くする
- 表示に時間を要する場合は、ローディング表示により待機状態を明示する
- AIによるプラン生成および説明補助は、通常の画面表示処理とは分離し、ユーザーが待機状態を認識できるUIとする

#### 7.3.3 DBアクセス設計

- ダッシュボードでは、必要最小限の情報のみ取得する
- 年間維持コストは保存項目ではなく、保存済み備えプランのうち updated_at が最新の1件を算出元として表示時に動的計算する
- 備蓄コスト目安も表示時算出とする
- 通知対象抽出や期限順表示に対応するため、stock_items (user_id, expires_at) および stock_items (expires_at) のインデックスを優先して利用する

#### 7.3.4 キャッシュ設計

Upstash Redis は、鮮度よりも再利用効果が高い箇所に限定して利用する。

想定対象は以下とする。

- 同一条件での備えプラン生成結果
- AI説明補助結果
- 商品マスタ一覧または一部商品一覧

以下の情報はキャッシュ対象の優先度を下げる。

- 契約状態
- 備蓄品一覧
- 通知対象判定
- 本人データのリアルタイム表示

### 7.4 対応内容

- 主要画面の表示速度確保
- ダッシュボードの取得項目絞り込み
- AI処理の待機UI
- AI説明結果や一部提案結果のキャッシュ利用
- 通知対象抽出を意識したDB設計

### 7.5 対象外内容

- 大規模負荷試験基盤
- 複雑な分散キャッシュ構成
- リードレプリカ
- 高度な非同期ジョブ分離
- CDNや画像最適化の細かいチューニング

### 7.6 実装・運用時の注意点

- ダッシュボードに情報を集約しすぎると表示遅延の原因となる
- キャッシュは整合性が崩れやすいデータに使いすぎない
- AI応答遅延時でも画面全体が操作不能にならないよう分離する
- 商品一覧表示とプラン生成結果表示は、固定商品マスタ前提でクエリを単純に保つ

## 8. ログ設計

### 8.1 目的

障害調査、通知処理確認、課金連携確認、AI失敗確認を可能にし、少人数運用でも問題の切り分けができる状態を実現することを目的とする。

### 8.2 設計方針

- 主要操作、エラー、決済結果、通知処理結果などをログとして保存または出力する
- 開発環境と本番環境でログレベルと出力内容を切り替える
- 本番では構造化ログを基本とし、処理単位で追跡可能にする
- 個人情報および機密情報はログ出力しない

### 8.3 設計内容

#### 8.3.1 ログ出力レベル

| 環境 | ログレベル | 出力方針 |
| --- | --- | --- |
| 開発環境 | debug / info / warn / error | 詳細確認を優先する |
| 本番環境 | info / warn / error | 障害調査に必要な情報へ絞る |

#### 8.3.2 ログ形式

- 本番環境では JSON 形式の構造化ログを基本とする
- 開発環境では人間が読みやすい形式でもよい
- API、通知、決済、AIなど、処理単位ごとに識別子を付与する

#### 8.3.3 必須ログ項目

| ログ種別 | 記録対象 | 主な記録項目 |
| --- | --- | --- |
| 認証ログ | サインアップ、ログイン、ログアウト | event_name, user_id, result, timestamp |
| APIログ | 主要API呼び出し | request_id, path, method, user_id, status, duration_ms |
| AIログ | プラン生成、説明補助 | request_id, user_id, feature, result, duration_ms, error_code |
| 通知バッチログ | バッチ開始・終了、送信集計 | batch_id, run_date, target_users, sent_count, failed_count |
| メール送信ログ | 送信結果 | batch_id, user_id, result, error_code |
| 決済ログ | Checkout開始、Webhook受信、契約反映 | request_id, user_id, stripe_event_id, result |
| 例外ログ | 想定外エラー | request_id, feature, message |
| 削除操作ログ | プラン削除、備蓄削除 | user_id, target_type, target_id, result |

#### 8.3.4 ログに出力しない情報

- パスワード
- 認証トークン
- Stripeカード情報
- APIキー
- Webhook署名
- メール本文全文
- OpenAIへ送信する全文プロンプト
- 家族情報の自由記述全文

### 8.4 対応内容

- 主要操作ログ
- エラーログ
- 決済結果ログ
- 通知処理結果ログ
- request_id、batch_id による追跡
- 開発環境 / 本番環境のログ出し分け

### 8.5 対象外内容

- SIEM連携
- 分散トレーシングの本格導入
- 高度な行動分析ログ
- 専用ログ分析ダッシュボード

### 8.6 実装・運用時の注意点

- 通知関連では user_id と stock_item_id の追跡性を確保する
- Stripe連携では stripe_event_id を必ず記録する
- 成功件数も残さないと異常の検知が難しくなる
- 個人情報露出やログ肥大化を避けるため、必要最小限の出力にとどめる

## 9. 可用性設計

### 9.1 目的

外部サービス障害や一部機能失敗が発生した場合でも、システム全体が直ちに利用不能にならず、必要な範囲で継続利用できる状態を確保することを目的とする。

### 9.2 設計方針

- MVPでは単一構成を前提とし、外部SaaSの可用性を活用する
- 障害時は機能単位で縮退運用する
- 通知・課金など再実行が必要な処理は冪等性を確保する
- 過剰な冗長構成は採用しない

### 9.3 設計内容

#### 9.3.1 可用性方針

- システムは常時利用可能であることを目指すが、厳密な商用SLAは設けない
- DB、認証、決済、AI、キャッシュ、メール送信は外部サービスに依存する
- 依存サービス障害時は、利用可能な機能のみ継続する

#### 9.3.2 縮退運用

| 障害対象 | 継続方針 |
| --- | --- |
| OpenAI API | 備えプラン生成・説明補助のみ停止し、他機能は継続利用する |
| Upstash Redis | キャッシュを使わず継続動作する |
| メール送信サービス | 通知送信は失敗として記録し、再実行可能な状態を保つ |
| Stripe Webhook | 再送受信を前提に冪等処理を行う |
| Supabase DB / Auth | 認証必須機能は影響を受けるが、公開ページは可能な範囲で表示する |

#### 9.3.3 再実行性・整合性

- 通知重複防止は stock_items.notified_30days_at および notification_logs によって担保する
- Stripe Webhook は同一イベントが再送されても問題ないよう冪等処理を行う
- Redis を正本データとして扱わず、キャッシュ層としてのみ利用する
- 重要処理は成功時のみ状態更新を行う

### 9.4 対応内容

- AI障害時の縮退
- Redis障害時の継続利用
- 通知バッチ再実行可能性
- Webhook冪等処理
- 通知重複防止

### 9.5 対象外内容

- マルチリージョン構成
- 自動フェイルオーバー基盤
- DRサイト
- ゼロダウンタイム最適化
- 高可用クラスタ構成

### 9.6 実装・運用時の注意点

- 外部依存先の失敗で画面全体が停止しないようにする
- 再実行前提の設計を通知とWebhookに必ず入れる
- キャッシュ障害を機能障害に直結させない
- 通知メール送信処理は定期実行で安定して動作することを重視する

## 10. セキュリティ設計

### 10.1 目的

個人情報、家族情報、備えプラン、備蓄情報、契約情報を保護し、MVPとして必要十分な安全性を確保することを目的とする。

### 10.2 設計方針

- 認証・認可とユーザーごとのデータ分離を最優先とする
- 基本的なセキュリティ対策を確実に実装する
- カード情報は外部決済サービスへ委譲し、自前保持しない
- AI機能は説明補助に限定し、安全判定機能として扱わない

### 10.3 設計内容

#### 10.3.1 通信・認証

- 本番環境では HTTPS / TLS を必須とする
- 認証は Supabase Auth を利用する
- 認証必須画面は未ログイン時にアクセス制御を行う

#### 10.3.2 認可・データ分離

本人所有データは、所有者本人のみ操作可能とする。

RLS適用対象は以下とする。

- users
- family_members
- member_allergens
- plans
- plan_items
- stock_items
- notification_logs
- subscriptions

マスタ系テーブルは以下の方針とする。

- products：認証済みユーザー全員が参照可能、一般ユーザーの更新・削除不可
- plans_master：認証済みユーザー全員が参照可能、一般ユーザーの更新・削除不可

また、サーバー側APIでも user_id を本人に限定し、RLSのみに依存しない二重防御を行う。

#### 10.3.3 入力値検証

サーバー側で以下を検証する。

- 必須項目
- 文字数上限
- 形式
- 数値範囲
- 日付妥当性
- enum値
- 賞味期限が購入日以前でないこと
- 数量が0以下でないこと
- 金額が負値でないこと

#### 10.3.4 一般的な脆弱性対策

- XSS への基本対策を行う
- SQL Injection への基本対策を行う
- SQLは文字列連結で組み立てず、安全なDBアクセス手段を利用する
- 不要なエラーメッセージ詳細をユーザー画面に表示しない
- AI利用時は、自由入力をそのまま高権限処理に使わない

#### 10.3.5 Stripe連携の安全性

- 決済は Stripe Checkout を利用する
- カード情報は自前で保存しない
- Webhookは署名検証を必須とする
- 契約状態更新はサーバー側のみで行う

#### 10.3.6 AI利用時の安全性

- AIは固定商品マスタ、家族条件、想定日数、候補の範囲、優先方針をもとにした備えプラン作成および説明補助のみに利用する
- 商品の最終安全判定、医療判断、絶対的保証は行わない
- 商品情報やAI提案を最終的な安全保証として見せない
- 画面上および必要な導線で、最終確認が必要である旨の注意文を表示する

### 10.4 対応内容

- HTTPS / TLS
- Supabase Auth
- RLS
- サーバー側本人チェック
- サーバー側バリデーション
- Stripe Webhook署名検証
- 秘密情報の環境変数管理
- XSS / SQL Injection 対策
- AIの利用範囲制限と注意文表示

### 10.5 対象外内容

- WAFの詳細運用
- HSMや秘密分散
- 外部脆弱性診断委託
- 高度な監査基盤
- 細かい権限ロール分離

### 10.6 実装・運用時の注意点

- RLS設定漏れが最も重大な事故要因になりやすいため、優先的に検証する
- サービスロールキーをクライアント側へ露出させない
- Webhookは署名未検証で処理しない
- AIの出力をそのまま安全保証として表示しない
- ログに機微情報を残さない

## 12. まとめ

本システムのMVPにおける非機能設計では、通知、課金、AI、認証認可といった壊れやすい機能を重点対象とし、少人数・短期間開発でも実装可能な範囲で、運用性、性能、ログ、可用性、セキュリティを確保する方針とする。

特に、本人データの分離、通知重複防止、Webhookの安全な処理、AI利用範囲の制限、通知処理の安定運用、主要操作の追跡可能性を重要項目とし、MVPとして必要十分な品質を確保する。

また、本設計は、固定商品マスタ前提、保存済みプランのみ保持、備蓄商品編集なし、見直し専用画面なし、通知はメールのみというMVPスコープに合わせ、過剰設計を避けた現実的な非機能設計として定義する。
