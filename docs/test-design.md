# テスト設計書

## 1. 文書概要

本書は、食物アレルギー家庭向け防災備蓄支援アプリ「そなえアレ」の MVP に対するテスト設計書である。

本テスト設計では、以下を目的とする。

- 主要ユーザーフローが成立することを確認する
- 画面 / API / 業務ルールの観点で、MVP に必要な品質を担保する
- 通知 / 課金 / AI / 認証認可など、事故につながりやすい領域を重点確認する
- 発表前に通すべきデモ導線を明確化する

本テスト設計は、単なる CRUD 確認ではなく、
主要導線が最後まで止まらないこと と 危険な誤動作を起こさないこと を重視する。

---

## 2. 対象範囲

### 2-1. MVP 対象機能

- ユーザー登録 / ログイン / ログアウト
- 家族構成・アレルギー情報の登録 / 取得 / 編集
- AI による備えプランの生成
- 防災食 / 日常転用品の候補表示
- 商品詳細表示
- 商品サイトへの遷移
- 備えプランの保存 / 一覧 / 詳細 / 削除
- 備蓄商品の登録 / 一覧 / 削除
- ダッシュボードでの期限・コスト・備蓄品一覧・料金プラン・保存済みプランの確認
- 賞味期限 30 日前のメール通知
- 通知メールから備蓄品一覧への導線
- 保存済みプラン一覧・備えプラン詳細を通じた再購入導線
- AI による説明補助
- 有料プラン決済 / 有料機能制御

### 2-2. MVP 対象外

- 商品情報の自動収集
- 価格 / 在庫のリアルタイム取得
- EC サイト内での決済完結
- 商品成分表の自動解析
- LINE 通知 / ブラウザプッシュ通知
- 通知条件の細かなカスタマイズ
- 高度な通知履歴管理
- 高度な比較 / レコメンド機能
- AI による最終安全判定
- 管理者向け商品運用画面
- 備えプランの編集
- 備えプランの版管理 / 差分比較 / 共同編集
- 備蓄商品の画面上での編集機能
- 見直し専用画面

## 3. 前提整理

### 3-1. テスト設計上の前提

主要フローは以下である。

- 会員登録 / ログイン
- 家族構成・アレルギー情報登録
- AI による備えプラン生成
- 候補商品の確認
- 備えプラン保存
- 備蓄商品登録
- ダッシュボード確認
- 賞味期限 30 日前通知
- 通知メールから備蓄品一覧遷移
- 必要に応じて備蓄削除 / 再購入判断

また、以下を前提とする。

- 備えプランに編集機能は存在しない
- 備蓄商品に編集機能は存在しない
- 見直し専用画面は存在しない
- 通知メールの遷移先は備蓄品一覧画面である
- 家族構成・アレルギー情報は family_members と member_allergens を基準に扱う
- 備えプランの「生成」と「保存」は分離される
- 家族メンバーは 1 人以上必須とする（0 人は登録不可）

---

### 3-2. 特に重要な業務ルール

| 業務ルール                                        | 確認ポイント                                 |
| ------------------------------------------------- | -------------------------------------------- |
| 提案対象は防災食 / 日常転用品の 28 品目不使用食品 | 対象外が混入しない                           |
| 生成と保存分離                                    | 保存しないと一覧に出ない                     |
| 編集機能なし                                      | UI / API が存在しない                        |
| 通知は 30 日前                                    | 日付判定が正しい                             |
| 1 日 1 回通知                                     | 重複しない                                   |
| 商品ごと 1 回                                     | 再送されない                                 |
| ユーザー単位 1 通                                 | まとめて送信される                           |
| 通知メールは備蓄品一覧画面へ遷移する              | 遷移先が正しい                               |
| 無料 / 有料の保存件数制御                         | 無料は 1 件、有料は webhook 後に複数保存可能 |
| AI は説明補助のみ                                 | 最終判断をしない                             |

### 3-3. テスト設計で重視すべき論点

- 主要フローが最後まで通るか
- 未入力 / 未登録 / 空状態 / 削除後状態が破綻しないか
- 無料 / 有料の制御が業務ルール通りか
- 通知の対象判定と重複防止が正しいか
- 認証 / 認可漏れがないか
- AI が役割逸脱しないか
- 外部連携（決済、メール、商品サイト遷移）が最低限安全に扱えるか
- 備蓄商品が編集なし前提でも運用フローが成立するか

## 7. 設計上の注意点

### 7-1. 実装上の注意点

#### 生成結果の扱い

生成結果を一時状態として扱うか、保存済みデータとして扱うかを曖昧にすると、未保存にもかかわらず一覧に表示される不整合が発生しやすい。

---

#### プラン保存仕様の誤解

最新スコープでは、備えプランは「保存 / 一覧 / 詳細 / 削除」のみとする。

編集機能を追加し始めると MVP の範囲を超えやすいため、仕様を明確にしておく。

---

#### 通知重複防止

単純な日次検索のみで通知処理を行うと、重複通知が発生しやすい。

通知済みデータを管理することを前提とし、その前提に沿ったテスト設計を行う必要がある。

---

#### 有料制御の反映タイミング

決済完了画面の表示のみで有料化したと扱うと、保存件数制御に不整合が生じる。

有料化は webhook 反映後を正とする。

---

#### 備蓄商品は編集できない前提の明確化

編集画面が存在しないにもかかわらず API で更新可能な状態にすると、仕様理解がずれやすい。

MVP では、備蓄商品は「登録 / 備蓄品一覧 / 削除」のみと明確にする。

---

### 7-2. テスト観点として抜けやすい点

- 家族構成・アレルギー情報未登録時の生成制御
- 一覧 0 件時の空状態
- 最後の 1 件削除後の状態
- 他人 ID を直接指定した参照 / 削除
- webhook 反映後の遅延 / 未反映
- 賞味期限 30 日前ちょうどの境界判定
- AI 失敗時のフォールバック
- 通知メールの遷移先が備蓄品一覧であること
- 備蓄商品に編集 UI が存在しないことが仕様通りであるか
- 備えプランに編集 UI / API が存在しないことが仕様通りであるか

---

### 7-3. MVP として削るべき過剰なテスト

- AI 文面の自然さに関する詳細評価
- レコメンド精度の高度な比較検証
- 高度な通知履歴管理の検証
- 管理者向け画面のテスト
- 版管理 / 差分比較の検証
- 外部 EC サイト側の挙動検証
- リアルタイム価格 / 在庫連携の検証
- 備蓄商品の編集機能を前提とした詳細 UI テスト
- 備えプラン編集を前提とした詳細 UI / API テスト
- 見直し専用画面を前提としたテスト

---

MVP では、業務ルールが破綻しないこと、主要導線が最後まで通ること、危険な誤動作が発生しないことを最優先とする。
