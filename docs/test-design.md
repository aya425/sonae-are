# そなえアレ テスト設計書

## 1. 文書概要

本書は、食物アレルギー家庭向け防災備蓄支援アプリ「そなえアレ」の MVP に対するテスト設計書である。

本テスト設計では、以下を目的とする。

- 主要ユーザーフローが成立することを確認する
- 画面 / API / 業務ルールの観点で、MVP に必要な品質を担保する
- 通知 / 課金 / AI / 認証認可など、事故につながりやすい領域を重点確認する
- 発表前に通すべきデモ導線を明確化する

本テスト設計は、単なる CRUD 確認ではなく、**主要導線が最後まで止まらないこと** と **危険な誤動作を起こさないこと** を重視する。

### 2-1. MVP 対象機能

- ユーザー登録 / ログイン / ログアウト
- 家族情報・アレルギー情報の登録 / 取得 / 編集

- 防災食 / 日常転用品の候補表示

- 見直し専用画面

## 3. 前提整理

### 3-1. テスト設計上の前提

本テスト設計では、主要ユーザーフローが成立することを重視する。

主要フローは以下である。

1. 会員登録 / ログイン
2. 家族情報・アレルギー情報登録
3. 備えプラン生成
4. 候補商品の確認
5. 備えプラン保存
6. 備蓄商品登録
7. ダッシュボード確認
8. 賞味期限 30 日前通知
9. 通知メールから備蓄一覧遷移
10. 必要に応じて備蓄削除 / 再購入判断

また、今回の最新スコープでは以下を前提とする。

- 備えプランに編集機能は存在しない
- 備蓄商品に編集機能は存在しない
- 見直し専用画面は存在しない
- 通知メールの遷移先は備蓄一覧画面である
- 家族情報は `family_members` と `member_allergens` を基準に扱う
- 備えプランの「生成」と「保存」は分離される

### 3-2. 特に重要な業務ルール

| 業務ルール                                                 | テスト上の確認ポイント               |
| ---------------------------------------------------------- | ------------------------------------ |
| 提案対象は防災食 / 日常転用品の 28 品目不使用食品          | 対象外商品が混入しないこと           |
| 備えプランは「生成」と「保存」を分離                       | 生成だけで保存済み一覧に入らないこと |
| 備えプランに編集機能はない                                 | 編集 UI/API が存在しないこと         |
| ダッシュボードでは期限・コスト・保存済みプランを確認できる | 集約表示が正しいこと                 |
| 通知はメールのみ                                           | 他通知手段前提の挙動がないこと       |
| 通知対象は賞味期限 30 日前                                 | 日付境界判定が正しいこと             |
| 通知は 1 日 1 回バッチ                                     | 同日複数回送っても重複しないこと     |
| 各備蓄商品への 30 日前通知は 1 回のみ                      | 再送されないこと                     |
| 同日通知対象商品はユーザー単位で 1 通に集約                | 商品ごとに複数通送られないこと       |
| 通知メールは備蓄一覧画面へ遷移する                         | リンク先が正しいこと                 |
| AI は説明補助のみ                                          | 医療判断 / 安全保証をしないこと      |
| 無料プランは保存済みプラン 1 件まで                        | UI / API 両方で制御されること        |
| 有料プランは複数件保存可能                                 | 決済反映後に制限解除されること       |
| 備蓄商品は画面上で編集できない                             | 編集 UI が存在しないこと             |

### 3-3. テスト設計で重視すべき論点

- 主要フローが最後まで通るか
- 未入力 / 未登録 / 空状態 / 削除後状態が破綻しないか
- 無料 / 有料の制御が業務ルール通りか
- 通知の対象判定と重複防止が正しいか
- 認証 / 認可漏れがないか
- AI が役割逸脱しないか
- 外部連携（決済、メール、商品サイト遷移）が最低限安全に扱えるか
- 備蓄商品が編集なし前提でも運用フローが成立するか

### 4-2. 観点分類の方針

本書では、テストを以下の 3 観点で管理する。

- 画面テスト
- API テスト
- 業務ルールテスト

加えて、発表準備のために **デモ確認** を別枠で持つ。

## 7. 設計上の注意点

### 7-1. 実装時にハマりやすい点

### 生成結果の扱い

生成結果を一時状態として扱うか、保存済みデータとして扱うかを曖昧にすると、未保存なのに一覧に見える不整合が起きやすい。

### プラン保存仕様の誤解

最新スコープでは、備えプランは**保存 / 一覧 / 詳細 / 削除のみ**とする。

編集機能を追加し始めると MVP の範囲を超えやすい。

### 通知重複防止

単純に日次検索だけで送ると重複通知が起きやすい。

通知済み管理を前提にし、その前提に沿ったテストを入れる必要がある。

### 有料制御の反映タイミング

決済完了画面を見せただけで有料化したと扱うと、保存件数制御がズレやすい。

有料化は webhook 反映後を正とする。

### 備蓄商品は編集できない前提を明確にする

編集画面がないのに API だけ更新可能だと仕様理解がずれやすい。

MVP では、備蓄商品は登録・一覧・削除のみと明確にしておく。

---

### 7-2. テスト観点として抜けやすい点

- 家族情報未登録時の生成制御
- 一覧 0 件時の空状態
- 最後の 1 件削除後状態
- 他人 ID 直打ちによる参照 / 削除
- webhook 後の反映遅延 / 未反映
- 30 日前ちょうどの境界
- AI 失敗時のフォールバック
- 通知メールの遷移先が備蓄一覧である点
- 備蓄商品に編集 UI が存在しないこと自体が仕様通りか
- 備えプランに編集 UI/API が存在しないこと自体が仕様通りか

---

### 7-3. MVP として削るべき過剰なテスト

- AI 文面の自然さの細かな評価
- レコメンド精度の高度比較
- 高度な通知履歴管理
- 管理画面系テスト
- 版管理 / 差分比較テスト
- 外部 EC サイト側の挙動検証
- リアルタイム価格 / 在庫連携の検証
- 備蓄商品の画面未提供編集機能を前提とした詳細 UI テスト
- 備えプラン編集を前提とした詳細 UI / API テスト
- 見直し専用画面を前提とした画面 / API テスト

MVP では、**業務ルール破綻がないこと、主要導線が止まらないこと、危険な誤動作をしないこと** を優先する。
